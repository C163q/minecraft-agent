# 单人存档进出时的输入结果

本规格适用于 Minecraft Java Edition 26.3 本地单人游戏。模型通过 `input_script` 在菜单进入已有存档、确认创建并进入新存档，或在暂停菜单选择保存退出时，应能从同一次调用知道旧输入是否已清理，并看到接下来可以操作的画面。

## 识别切换

选择在 Mod 观察原版开始打开、创建或退出本地存档的调用，并关联当时已接受的输入请求。只在 `ClientLevel` 改变时处理会漏掉“点击在末拍启动加载，`END` 先到”的情形，也会混入换维度和重生。Rust 事后补调 `inspect_game` 能看到另一帧，但无法恢复已中断请求的拍数和事件。

26.3 字节码中，`WorldOpenFlows.openWorld` 负责打开已有存档。原版创建界面从 `CreateWorldScreen.onCreate` 经过创建确认，进入 `WorldOpenFlows.createLevelFromExistingSettings`；测试探针另有直接调用 `createFreshLevel` 的路径。`Minecraft.doWorldLoad` 启动内置服务器之前会先调用 `disconnectWithProgressScreen`。保存退出的菜单路径进入 `Minecraft.disconnectFromWorld`，本地分支经过保存界面后才设置标题页。实现需要识别最初的操作，并跟踪这一条流程，避免将加载内部的清理步骤解释为第二次退出。仅浏览存档列表、填写世界名称、按 Esc 打开暂停菜单时，普通 `END` 照常返回。

## 旧输入的边界

创建目录可能在进入服务器加载方法之前就失败。创建流程从最终确认后的原版创建入口观察，并检查其提前失败分支。备份等询问也可能通过异步回调继续打开存档。首次停在询问界面返回 `needs_input` 后，只有随后实际点击继续的请求才接管这次操作；即使它的末拍就是确认，也要等待自己的结果。

切换开始时停止派发旧输入，清除所有旧块、函数、监听、待处理事件动作和鼠标移动余量，释放脚本保持的键与按钮。清理可发生在一次按钮派发的回调栈中；同拍还未派发的其他输入也应丢弃。已开始派发且触发切换的输入拍计一次，渲染、加载、保存和等待暂停确认都不计输入拍。保留本次调用已经记录的 `events` 与省略条数。已注销的旧监听不能在目的地继续执行。

在调用原版回调前记住当前派发拍，切换开始时使这次派发失效。在回调内重入加载渲染或回到外层键鼠循环时，均不得重复计拍、重复发释放事件或发送同拍剩余动作。验收要包含一次点击之后同拍还有第二个输入的情况。

等待过程占用原请求，不阻塞客户端渲染或内置服务器。新存档可操作前允许原版完成加载。客户端有当前本地玩家、连接已就绪、加载界面与遮罩结束后，沿用 [END 的服务端确认及停止帧](../../development/README.md#end-的返回条件)。退出时等待原版退出流程结束，取最终菜单实际绘制的一帧。握手后尚未接受的脚本、工具取消、异常断线、传送门和死亡重生继续遵循各自现有语义。

## 返回约定

建议用以下字段表示一次已完成的退出，示例省略图像元数据。

```json
{
  "pause_reason": "world_changed",
  "transition": {"direction": "leave", "status": "completed", "input_cleared": true},
  "ticks": 2,
  "world": "not_needed",
  "screen": "TitleScreen",
  "events": []
}
```

进入存档时 `direction` 为 `enter`，完成后 `world` 为 `paused`。`screen` 沿用 `inspect_game` 的遮罩优先规则，普通世界视图为 null。两个方向都沿用 `include_screenshot`（默认 true），图片与状态属于同一帧，截图 ID 可交给 `cursor_hint`。`input_cleared` 表示 Mod 已完成上述旧输入清理。

建议以切换开始后的 **30 秒墙钟时间**作为等待完成的上限。在期限内出现需要玩家操作的原版确认界面时，立即返回该界面并标记 `needs_input`；原版明确取消或失败时分别标记 `cancelled` 或 `failed`，保留可观察的界面。期限届满仍在加载或保存时标记 `in_progress`，返回当前界面和实际暂停状态。若客户端无法提供有效帧，应有界地返回观测错误，避免伪造完成画面。已返回的请求随即结束；之后由模型调用 `inspect_game` 查看进展，加载完成后不会由过期请求突然暂停世界。真实通信错误仍按工具错误返回。

26.3 等待内置服务器退出时会直接调用 `renderFrame(false)`。过渡帧由实际绘制完成的回调观察，期限使用单调时钟；超时或取消须能使原请求失效，即使原版已丢弃普通客户端任务。游戏对象与清理动作仍归客户端线程。随后到达的暂停标记和截图回调只能完成所属请求。

## 验收

- 从原版菜单通过正式 MCP 进入已有测试存档、确认创建新存档、保存退出。分别覆盖末拍点击后紧跟 `END` 和点击后还有剩余动作。检查实际输入拍数、目的地界面、同帧截图和 `include_screenshot: false`。
- 准备旧队列、监听和保持状态，检查 `inspect_input` 与目的地实际输入均已清空。检查切换前命中的事件仍在原调用的结果里。进入后对照服务端暂停状态，退出后确认取得最终菜单。
- 核对纯菜单操作、原版询问或加载失败、超时、调用取消和迟到的渲染回调。运行现有跨维度死亡与重生、换维度中断及[退出过程中的只读查询](../../../tests/game/game_state.py)用例。
