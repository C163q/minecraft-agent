# 26.3 玩家受伤与客户端生命值更新

本文核对 Minecraft Java Edition 26.3 原版 JAR，依据 JDK 的 `javap -p -c` 输出。目标是找出脚本事件 `HpLost` 可观察的原版信号。以下调用路径来自字节码，尚未用实机探针记录事件次数和先后顺序。

## 服务端的伤害事件

- `Player.actuallyHurt` 计算护甲和效果减伤，再扣除吸收生命。剩余伤害为零时直接返回。有剩余伤害时，调用 `setHealth(getHealth() - damage)`，随后发出 `GameEvent.ENTITY_DAMAGE`。在这条路径上，只损失金色吸收心不会发出该事件。该事件描述服务端伤害结算，单独观察它无法确定客户端何时收到新的生命值。
- `LivingEntity.hurtServer` 对服务端玩家调用进度触发器 `CriteriaTriggers.ENTITY_HURT_PLAYER`，传入伤害来源、伤害数值和格挡标志。客户端另有 `ClientboundDamageEventPacket`，其中包含实体和伤害来源信息，没有玩家扣血后的生命值。

### 原版接受一次受伤的判定

在普通玩家伤害路径上，`ServerPlayer.hurtServer` 返回该次伤害是否被接受。免疫、受伤冷却期间被拒绝的重复命中、盾牌完全格挡均可返回 `false`。金心完全吸收时，虽然 `Player.actuallyHurt` 提前返回，外层仍可返回 `true`。原版用浮点数结算，正的微量伤害可以通过同一分支。

原版的客户端伤害广播只覆盖部分已接受的命中。例如在受伤冷却期内，普通攻击的伤害强于上一次时，原版可以按差额结算并返回 `true`，同时跳过新一轮伤害广播。因此若脚本需要逐次观察原版接受的伤害，可以由内置服务器在本地玩家的 `hurtServer` 返回成功后发送通知。客户端接到通知的时序和每次结算的通知次数仍需实机核对。

## 客户端的生命值变化

`ServerPlayer.doTick` 将当前生命值与上次发送的值比较，生命值、食物值或饱和度的零值状态变化时可发送 `ClientboundSetHealthPacket`。`ClientPacketListener.handleSetHealth` 将包中的普通生命值传给 `LocalPlayer.hurtTo`。首次处理时直接设置初值；此后原版比较旧值与传入值，下降时设置受伤计时。相同生命值也可能出现在包里，例如仅饥饿值发生变化时。项目的[停止同步](../../mod/src/main/java/mcagent/Playback.java)也会发送当前生命值。

`LivingEntity.getHealth` 和 `setHealth` 读写同步字段 `DATA_HEALTH_ID`。字段的写入，以及 `ClientPacketListener.handleSetEntityData` 应用实体数据包，都会经由 `SynchedEntityData` 在写入后调用实体的 `onSyncedDataUpdated(EntityDataAccessor<?>)`。本地玩家已有这个回调。吸收生命有单独的字段。

对脚本而言，候选观察点是本地玩家的逐字段更新回调：筛选普通生命值，维护同一玩家上一次已观察到的值，只在下降时通知输入调度器。这样客户端依次应用 20、16、20 时可识别中间的下降，连续收到相同的 16 时只触发一次。客户端只收到 20、20 时，无法从这两个值推断服务端曾掉血。进入世界和重生时建立基线的时机、实体数据与生命值包的实际到达顺序，以及停止同步期间的通知时序仍待实机验证。

此前的[停止帧实测](2026-11-21-world-stop-frame.md)验证了普通伤害同步后可在截图中看到新红心。该实测只验证画面，不涉及监听回调的次数。
