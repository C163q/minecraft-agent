# 普通键盘输入与 END 的停止边界

2026-11-21 在 Minecraft Java Edition 26.3、Fabric Loader 0.20.1、OpenJDK 27.0.1.1 上运行独立图形客户端，使用平坦测试世界和默认移动键位。实验沿用[保留当前界面的暂停方式](2026-11-21-container-pause.md)。

## 脚本与采样

第一段脚本包含一行顶格注释、两行缩进注释和连续两次 W。缩进注释各占一拍，顶格注释跳过。

```text
BEGIN
// comment
  // idle
Key(w)
Key(w)
  // release
END
```

服务端确认暂停后等待十秒，再提交第二段。第二段按下 A，下一行是真正的空行，应释放 A，W 在两拍中都应处于松开状态。

```text
BEGIN
Key(a)

END
```

探针在未暂停的客户端 tick 入口比较相邻行，按状态变化向 `KeyboardHandler.keyPress` 发送按下或释放事件。它在 `KeyboardInput.tick` 返回时读取游戏生成的 `Input.forward()` 和 `Input.left()`。最后一行被消费时发出暂停请求，并继续统计玩家输入被额外消费的次数。客户端在本帧 `Minecraft.runTick` 返回时报告暂停；服务端在自己的 `IntegratedServer.tickServer` 返回时报告暂停。两个报告时间相对于最后一行的消费时刻，包含观测点本身的延迟。

服务端世界时钟在主世界 `ServerLevel.tickTime` 返回时发布快照，输入线程在最后一行读取最近发布的值；暂停确认后另在服务端线程直接读取世界时间。实验记录的是世界时钟与输入的相对进度，其分辨率为一个世界 tick。

## 正常帧率与低帧率对照

低帧率组在每个渲染循环开始时延迟 310 ms，使客户端在一帧内补跑多个 tick。最后一组额外测试一种临时处理：消费完最后一行后，若仍在同一帧且原版暂停标志尚未生效，则跳过后续的 `Minecraft.tick()` 调用，最后一行所属的 tick 自身仍能完成。每组各运行一次 W 段和一次 A 段。

| 条件 | 段 | 实际移动输入 | END 后额外读取次数 | 世界时间（提交前 / 最后一行 / 暂停确认后） | 客户端 / 服务端报告暂停耗时 |
| --- | --- | --- | ---: | --- | --- |
| 正常帧率 | W | 空、W、W、空 | 0 | 22 / 26 / 26 | 6.87 / 50.65 ms |
| 正常帧率 | A | A、空 | 0 | 26 / 28 / 28 | 6.99 / 60.11 ms |
| 低帧率 | W | 空、W、W、空 | 2 | 28 / 34 / 35 | 22.10 / 79.93 ms |
| 低帧率 | A | A、空 | 4 | 35 / 41 / 41 | 11.15 / 54.64 ms |
| 低帧率，跳过同帧剩余 tick | W | 空、W、W、空 | 0 | 41 / 48 / 48 | 3.45 / 59.52 ms |
| 低帧率，跳过同帧剩余 tick | A | A、空 | 0 | 48 / 54 / 54 | 4.17 / 29.53 ms |

三组中的 W 都只发送了一次按下和一次释放。正常帧率下四行在四个不同的帧被消费；两组低帧率测试中四行均在同一帧被消费。每组在 W 段暂停确认十秒后，客户端位置、服务端世界时间与额外输入计数保持不变；随后 A 段从第一行开始，两拍均未读到 W。

`Minecraft.runTick` 先循环处理积累的客户端 tick，再更新帧末暂停标志，解释了同一帧内额外读取的来源。临时跳过剩余 tick 可以守住本实验的客户端输入边界；其对界面和其他子系统的影响仍待验证。内置服务器独立推进，即使客户端严格消费了四行，服务端在这次低帧率实验中也可能已推进七拍。接口报告可以分别记录已消费行数与已确认暂停的世界状态。若要提供每行恰好一个世界 tick 的保证，还需验证服务端步进与输入消费的同步。

## 复核范围

探针源码、构建和启动脚本保存在本机 `.tmp/input/`，在该目录依次运行 `python3 build.py` 和 `python3 launch.py` 可创建新的独立实例。六个样本和断言结果保存在 `run-838rrd7s/console.log` 的 `PROBE` 行，进程退出码为 0。该实验使用游戏键盘事件处理入口，覆盖默认键位 W、A、空行、注释与两个连续输入块。Rust MCP、通用脚本解析器和精确的服务端步进尚未接入。
