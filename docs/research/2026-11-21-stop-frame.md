# 暂停确认、箱子状态同步与停止截图

2026-11-21，在 Minecraft Java Edition 26.3、Fabric Loader 0.20.1、OpenJDK 27.0.1.1 的独立单人世界验证。采用[保留箱子界面的暂停方式](2026-11-21-container-pause.md)。本次使用 Fabric 探针及游戏原生截图接口；用像素定位目标格来模拟一次下一步决策。

## 观测方法

1. 打开空箱子并截取基准帧。服务端在一个运行中的 tick 末尾将一颗钻石放入前三格之一，调用容器的 `broadcastChanges()` 发出更新，并请求暂停。六轮使用三个不同的目标格。
2. 在客户端 `handleContainerSetSlot` 返回处检查实际菜单槽位，记录更新应用时刻。服务端在第一次确认暂停的 `IntegratedServer.tickServer` 返回处记录该标记与世界时间，随后在同一连接发送带本轮编号的 `ClientboundPingPacket`。客户端的 `handlePing` 会调度到客户端线程。探针只在该处理函数返回后接受本轮标记。
3. 在标记到达时，以及随后的 `renderFrame` 完成时，各从 `GameRenderer.mainRenderTarget()` 调用 `Screenshot.takeScreenshot`，等待 GPU 读回并生成 PNG。分别比较三格的像素与空箱子基准。低帧率组在每个客户端帧开头延迟 175 ms，渲染前再延迟 125 ms，保留游戏原有的数据包队列顺序。
4. 保持暂停，复查世界时间、箱子界面和像素。恢复后，根据最终 PNG 与空箱子基准的像素差选格，通过箱子界面的鼠标按下和释放事件点击。服务端检查该格已空、玩家指针上持有钻石。

## 最后一拍已经改动但尚未发出的槽位

另外两轮都把钻石放入第 2 格，省略写入后的主动广播，并在服务端暂停时发送第一枚同连接标记。普通调度下，原版有机会在后续运行中同步箱子，第一枚标记后的截图已经显示钻石。

作为边界对照，探针在最后一个运行中的服务端 tick 尾部短暂等待客户端暂停标志，使写入后直到服务端确认暂停都没有再运行一拍。结束 tick 和暂停时的世界时间均为 57。此时服务端槽位已有钻石，客户端处理第一枚标记并重新渲染仍看到空格；额外保持暂停两秒以上再次采样，画面仍空，客户端也没有记录到相应的槽位更新。

在同一次暂停中，服务端主动调用当前菜单的 `broadcastChanges()`，紧接着发送第二枚标记。客户端应用了槽位更新后，标记处读出的上一帧仍空，之后渲染的第 2 格出现钻石。再保持暂停十秒，格子像素和世界时间稳定，恢复后按截图点击成功。固定边界的等待仅用于构造可复现的时序。

## 对工具返回时机的含义

本实验支持箱子界面的以下返回条件：内置服务端确认暂停，在服务端线程同步当前容器待发送的可见变更，随后通过同一连接发送请求专属标记；客户端处理标记后完成一帧包含该界面的新渲染，并完成该帧的图像读回，再一起返回暂停状态和截图。仅等待暂停、延迟固定毫秒数或确认收到标记，分别遗漏了不同阶段。标记只覆盖排在它之前且沿这条处理路径传递的消息。

结论覆盖本地单人世界中的箱子槽位和基于该界面的点击决策。实体位置、玩家血量 HUD、异步区块绘制、窗口缩放及 Rust MCP 到模型的传图尚待各自验证。

## 本机复核

源码与脚本位于 `.tmp/stop-frame/`。在该目录运行 `python3 build.py`，然后分别运行 `python3 launch.py`、`python3 launch.py --deferred` 和 `python3 launch.py --last-tick`。三次运行分别对应目录 `run-h1botsq4/`、`run-ya50jdje/`、`run-jrhtd05j/`。各自的 `console.log` 保留原始采样，进程均以状态 0 退出。每组截图由同名前缀及 `empty`、`before-render`、`ready`、`held` 标识；两个补充实验另保存第一枚标记对应的 `marker-only` 和 `marker-only-held` 图片。
